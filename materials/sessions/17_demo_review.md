# コマ17: 発表・振り返り

## 今日のゴール

完成した自分の `mycc.py` を、他人に説明できる形にする。

この回では新しい構文もコードも追加しない。
使うのはすべて手元にあるもの — 自分の `final/mycc.py`、`final/tests/` の17本（fixed17）、
[RV64 シミュレータ](../../tools/app.html?mode=run) だけである。

コマ16 で「動くコンパイラ」は完成した。
この回でやるのは、それを「説明できるコンパイラ」に変えることである。
自分の設計を言葉にできて初めて、次に何を足すべきかが判断できるようになる。

## この回で行うこと

| 作業 | 内容 | 目安 |
|------|------|------|
| 発表 | 自分の `mycc.py` の設計を10分で説明する | 10分 + 質疑5分 |
| 読解デモ | 生成アセンブリを1本、命令単位で読み下す | 15分 |
| 振り返り | コマ16 からコマ1 へ逆順にたどり、どの回で何が解けるようになったかを言い直す | 20分 |
| 自己レビュー | ルーブリックで自分の到達度を判定する | 15分 |
| 次の選択 | 発展課題26トピックから次にやるものを決める | 15分 |

## 発表の型

「何を作ったか」ではなく「**どう設計したか**」を話す。
動いていることは fixed17 が示すので、発表で証明する必要はない。

次の5点をこの順で話すと、10分にちょうど収まる。

| # | 話すこと | 具体例 |
|---|---------|--------|
| 1 | 入力から出力までの一本道 | C ソース → `preprocess()` → Lexer → Parser → `codegen()` → RV64 アセンブリ、のどこを自分が書いたか |
| 2 | いちばん重要な設計判断 | `codegen()` と `codegen_lval()` を分けたこと。なぜ1つの関数では書けないか |
| 3 | データをどう持ったか | ローカル変数表・`self._globals`・`self._struct_defs` のそれぞれが何を持ち、いつ引かれるか |
| 4 | 詰まったバグと、その切り分け方 | 症状 → 疑った場所 → 実際の原因 → どう気づいたか、の4段で話す |
| 5 | いま分かっている弱点 | 短絡評価が無い、エラーメッセージが不親切、など。直せていないことを隠さない |

**4 が発表の中心である。** 動いた話より、動かなかった話のほうが聞き手の役に立つ。
「アラインメントを16バイトに揃え忘れて `Illegal instruction` が出た」のような、
症状と原因が結びつかない種類のバグは、共有する価値がとくに高い。

聞く側は、発表ごとに次の1つを質問する。

- 自分の実装と違うやり方をしている箇所はどこか。なぜそちらを選んだのか

同じ仕様から出発しても、変数表の持ち方・型情報の表し方・エラーの出し方は人によって違う。
その差がどこから来ているかを聞き出すのが、この回でいちばん学びの多い部分である。

## 読解デモ: 生成アセンブリを1本読み下す

発表とは別に、**自分が生成したアセンブリを1本選んで、命令単位で説明する**。
コマ16 の完成チェックリストにある「生成アセンブリを1つ以上読んで、どこで何をしているか説明できる」を、
実際に声に出して確かめる作業である。

題材は `final/tests/f09_recur.c` を勧める。再帰フィボナッチなので、
プロローグ・エピローグ、引数の受け渡し、`ra` の退避、条件分岐、`call` の前後が
1つのプログラムに全部入っている。

```bash
python3 final/mycc.py final/tests/f09_recur.c > f09.s
```

出力した `f09.s` を [RV64 シミュレータ](../../tools/app.html?mode=run) に貼り付けると、
1命令ずつ進めながらレジスタとスタックの変化を見られる。

読み下すときは、次の問いに順に答える。

| # | 問い | 見るところ |
|---|------|-----------|
| 1 | `fib` の1回の呼び出しで、スタックは何バイト伸びるか | プロローグの `addi sp, sp, -N` |
| 2 | 戻り先アドレスはどこに退避されているか。なぜ退避が要るか | `sd ra, ...` と、その直後の `call` |
| 3 | 引数 `n` はどのレジスタで渡り、どこに置き直されるか | `a0` と、それを `s0` 相対へ書く `sd` |
| 4 | `n <= 1` の判定結果は、どういう値としてどこに残るか | 比較命令と `beqz` の組 |
| 5 | `fib(n-1) + fib(n-2)` で、前半の結果はどこに待避されるか | 2回目の `call` を挟む push / pop |
| 6 | `return` はどこへ飛ぶか。関数の出口は何個あるか | 共通エピローグラベルへの合流 |

6 まで答えられれば、自分のコンパイラが RV64 の呼出し規約をどう実現しているかを
説明できたことになる。答えに詰まった問いがあれば、それが次に読み直すべき自分のコードである。

## 振り返り: コマ16 からコマ1 へ逆順にたどる

進むときは「今日は何を足すか」で見ていたが、振り返りは逆に見る。
**「この機能を外したら、何が書けなくなるか」**を、最後の回から順に問う。

[`getting_started.md` の「全体の流れ」](../../workbook/docs/getting_started.md)の表を下から上へたどり、
各回について次を1文で言う。

> コマNN が無かったら、`___` が書けない。

たとえば次のようになる。

| コマ | 無かったら書けないもの |
|------|---------------------|
| 15 | 複数ファイルに分けたプログラム。`#define` による定数 |
| 14 | 関数をまたいで共有する状態。`!` と `&&` を使った条件 |
| 13 | ヒープ上に伸びる連結リスト |
| 12 | 意味のまとまりを持つデータ。`->` によるアクセス |
| 11 | 画面への出力そのもの |
| 10 | `int` と `char` の区別。ポインタを1つ進める、という操作 |
| 9 | `*p = v;` の左辺。ポインタを引数に取る関数 |
| 8 | 再帰。そもそも `main` 以外の関数 |
| 6 | 繰り返し |
| 5 | 分岐 |
| 4 | 変数 |
| 3 | 実行できるアセンブリ |
| 2 | AST を意味へ変換する、という発想そのもの |
| 1 | 動作を確認する手段 |

上の表は例であり、答えは1つではない。自分の実装で言い直すことに意味がある。

機能ごとの正確な導入回と検証テストは
[`language_spec.md` の対応表](../../workbook/docs/language_spec.md#feature-map)で引ける。
記憶と食い違ったらそちらが正しい。
各コマ終了時点で何が書けるかの実例は
[`code_example.md`](../../workbook/docs/code_example.md) にある。

この逆順のたどり直しは、発展課題を選ぶときの下準備でもある。
「自分がいちばん薄いと感じた層」が、次に手を入れるべき層である。

## 自己レビュー・ルーブリック

各項目を A / B / C で自己判定する。他人と比べるためのものではなく、
**次にどこへ手を入れるかを決めるための道具**である。

| 観点 | A | B | C |
|------|---|---|---|
| 動作 | fixed17 が全通する | 1〜3本落ちるが原因は特定できている | 落ちる原因が分からない |
| 説明 | 入力から出力までを図なしで説明できる | 資料を見れば説明できる | どこから話すか決められない |
| 設計 | `codegen()` / `codegen_lval()` を分ける理由を、分けない場合の破綻で説明できる | 分かれていることは説明できる | 役割の違いを言えない |
| 型 | `ty_str` が何を担い、どこで引かれるかを説明できる | 型サイズの計算だけ説明できる | 型情報の流れを追えない |
| アセンブリ | 生成物を命令単位で読み下せる | 全体の骨格は読める | 読んだことがない |
| 切り分け | 落ちたテストを最小の入力へ縮められる | 該当するコマの小さいテストまで戻れる | 総合テストの入力を直接読んでいる |
| 可読性 | 他人が読んで関数の責務が分かる | 自分は読める | 自分でも読み直しに時間がかかる |

C が付いた行が1つでもあれば、発展課題より先にそこを埋めるほうが効く。
とくに「動作」が C のままで発展課題に進むと、
`golden.py` による回帰確認が意味を持たなくなるので、先に fixed17 を通す。

## 次にどこへ行くか

[選択制の発展課題](../../workbook/advanced/README.md)は26トピックある。
どれも並列で、決められた順序は無い。

**コマ16 を終えた時点で、前提コマの条件はすべて満たしている。**
一覧表の「必須の前提」列に出てくるコマ番号は、コマ16 を待たずに先取りしたい人のための情報であり、
この時点では選択の制約にならない。残るのはトピック間の前提（F1 は F0 の後、O2 は O1 の後、など）だけである。

したがって選ぶ基準は「やれるかどうか」ではなく「何を得たいか」になる。

| 得たいもの | 系列 | 得られること |
|-----------|------|-------------|
| ブラックボックスを無くしたい | F | 提供された Lexer / Parser を自分の実装で置き換える。コンパイラの入口がブラックボックスでなくなる |
| 生成コードを速くしたい（軽く） | B | 定数畳み込み・ピープホール・末尾呼び出し。測定基盤なしで始められ、効果が目で見える |
| 生成コードを速くしたい（本格） | O | 測る → 解析する → 変換する、を積み上げる。O1 から順に積む前提があり、いちばん長い |
| OS とライブラリの下を見たい | R | libc なしで動かし、`printf` と `malloc` を自分で書く |
| 仕様がCとわざと違う点を埋めたい | S | 短絡評価・32bit 演算・構造体の代入。仕様の内側にある「実際のCとのずれ」を消す |
| 仕様の外の機能を足したい | L | ポインタ同士の引き算・複合代入・可変長引数の定義。意味を自分で決めて設計する |
| 誤りを実行前に見つけたい | Q | 型検査パスを足し、エラーをまとめて報告する |
| 自分自身をコンパイルさせたい | P | Python 版を C へ移植する。**方針のみが与えられ、自動採点は無い**長期の自主課題 |

各トピックの正確な前提・所要コマ数・完了条件は
[発展課題の索引](../../workbook/advanced/README.md)が唯一の出典である。
上の表は選ぶきっかけであって、索引の代わりではない。

迷ったときの目安は次の通りである。

- **自己レビューで C が付いた層**があるなら、そこに近い系列を選ぶ
- 短い時間で達成感を得たいなら **F0** か **B1**
- 何回かに渡って積み上げたいなら **O1** から
- P1 は他と性質が違う。複数回に渡り、自動採点も無い。それを承知のうえで選ぶ

## 注意

この回では新しい構文を追加しない。
`language_spec.md` の全機能はコマ15 までに実装済みで、コマ16 で統合まで終わっている。
新しく書かせるコードが無いことは、この回の欠落ではなく設計である。

発表は「完成した人の報告会」ではない。fixed17 が全通していなくても発表する。
どこで詰まり、何を試し、どこまで原因を絞れたかは、通ったテストの本数より情報量が多い。

自己レビューのルーブリックは自己申告であり、採点ではない。
A を付けたい欲求より、C を正直に付けて次の一手を決めるほうが得をする。

発展課題は選択制である。1つも選ばず、`final/mycc.py` の読みやすさとテストの追加に
時間を使う選択も同じだけ正当である。
