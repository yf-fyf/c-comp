# ポインタ同士の引き算 — 差は「要素いくつ分か」

## 今日のゴール

`p - q`（ポインタ同士の引き算）は、この仕様がまだ意味を決めていない機能である。
本物の C の慣習にならい、**要素いくつ分離れているか**を返す意味を与えて実装する。

### なぜ L 系なのか

S 系と L 系は、**その回で作る振る舞いの「正解」がどこに書いてあるか**で分かれる。
仕様が意味を決めている構文の、仕様と実装のずれを埋めるのが S 系。
仕様が対象外と決めた機能に、意味を自分で決めて足すのが L 系である
（[発展課題の索引](../../workbook/advanced/README.md)の「S と L の判定基準」節）。

S1 は「仕様が C とわざと違えている `&&` / `||` の意味論を、C の側へ寄せる回」、
S2 は「仕様が要求している 32 ビットの折り返しに実装のずれを合わせる回」で、
どちらも仕様の該当行から出発する S 系である。
この回はどちらとも違う。仕様は**ポインタ同士の減算・ポインタの関係比較を
「無い」と明示的に除外している**ので、埋めるべきずれがそもそも存在しない。
これは意味論の付け替えでも実装のずれでもなく、
**仕様が意図的に落とした機能を、意味を自分で決めて追加する回**——
すなわち判定基準どおりの **L 系**である。

> **この回は 2026-08-01 に `S3_ptrdiff` から `L1_ptrdiff` へ改名した。**
> 以前は判定が L 系なのに ID が `S3` のままという食い違いがあり、それを解消した。
> ラッパーも S ファミリの `semcc.py` から L ファミリの `langcc.py` に変わっている。

## コマ10 でやり残したこと

コマ10 では、ポインタと整数の演算に**要素サイズを掛ける**ことを学んだ。

```c
int *p;
p + 2;      // 2 * sizeof(int) = 8 バイト進む
p - 1;      // 4 バイト戻る
```

いまの実装は、この「ポインタ ± 整数」を正しく処理している。
しかし C には、もう1つのポインタ演算がある。

```c
int *p;
int *q;
q - p;      // ポインタ同士の引き算
```

これは**アドレスの差ではなく、要素いくつ分離れているか**を返す規則になっている。

```c
int *a;
int *p;
int *q;
a = malloc(sizeof(int) * 10);
p = a;
q = &a[7];

q - p;      // C の答え: 7(要素7個分)
```

いまの実装は `sub` するだけなので、**28**（バイト差）を返してしまう。

::: important

これは S2（32 ビットの折り返し）のような「未定義動作（符号付きオーバーフロー）の範囲内で、
選んだ挙動からずれている実装の詳細」とも違う。
仕様書はそもそも `p - q` の意味を定めていない
（`p - q` はポインタ同士の減算として明示的に除外されている）。
何も足さずに `Sub` の既存コード生成へ流すと、たまたま `sub` 命令が
そのまま出てバイト差が返ってしまう——だがこれは「仕様違反」ではなく、
**単に誰も意味を決めていない**だけである。コマ10 のテストは `a[i]` と
`*(p + 2)` しか書いていないので、`q - p` を書いた人だけが
「なぜか7倍ずれる」現象に出会う。

:::

## なぜ「要素数」なのか

一貫性のためである。C のポインタ演算は、次の等式が成り立つように設計されている。

```text
(p + n) - p  ==  n
```

`p + n` が「n 要素進む」なら、その差は「n」でなければ辻褄が合わない。
`p + 2` は 8 バイト進むが、`(p + 2) - p` は 2 になる。

この規則のおかげで、次のような書き方が自然にできる。

```c
int my_strlen(char *s) {
    char *p;
    p = s;
    while (*p != 0) { p = p + 1; }
    return p - s;        // 進んだ「文字数」がそのまま長さ
}
```

`char` は1バイトなので、この場合はバイト差と要素数が一致する
（だから `char*` では誤りが表面化しない）。
`int*` や構造体ポインタで初めてずれる。

## どう直すか

引き算のあとに、要素サイズで割る。

```text
      左辺を評価して退避
      右辺を評価
      sub a0, a1, a0      ← アドレスの差(バイト数)
      li  a1, 4           ← 要素サイズ
      div a0, a0, a1      ← 要素数に直す
```

要素サイズが 1（`char*`）のときは、割り算を出す必要がない。

判定も要る。`Sub` ノードは3種類が同居している。

| 式 | 型 | 生成 |
|----|----|------|
| `p - q` | ポインタ − ポインタ | **今回追加**: 引いてから割る |
| `p - 3` | ポインタ − 整数 | 既存: 3 に要素サイズを掛けてから引く |
| `i - j` | 整数 − 整数 | 既存: そのまま引く |

左右の型を `cg._type_of_expr()` で調べ、**両方がポインタのときだけ**新しい生成に回す。

::: note

**結果の型も変わる。**
`p - 3` の型はポインタ（`int*`）だが、`p - q` の型は**整数**である。
そうでないと `(q - p) + 1` がポインタ演算になり、1 ではなく 4 足されてしまう。
この型の修正はラッパー `langcc.py` の側で行っている（`_type_of_expr` の差し替え）。
本物の C では、この型に `ptrdiff_t` という名前が付いている。

:::

## 発展課題

1. **ポインタの関係比較**: `p < q` はこの仕様ではポインタの関係比較ごと
   「無い」機能である。追加するなら、何を決める必要があるか
   （符号付き比較でよいか、`==`/`!=` とは扱いが違うか、など）
2. **負の差**: `p - q` で `p < q` のとき、結果は負になる。
   `div` は符号付き除算なので正しく動くはずだが、実際に確かめる
3. **要素数の持ち回り**: この言語には配列型が無いので
   `sizeof(a) / sizeof(a[0])` という定番の書き方はそもそも書けない。
   `malloc` した領域の要素数をどう持ち回ればよいか
   （たとえば個数を別変数で保持する）を考える
4. **異なる型のポインタの差**: `int *p; char *s; p - s;` は C では**コンパイルエラー**である。
   Q1 の型検査に「ポインタ同士の引き算は同じ型でなければならない」を追加する
   （※この課題は L1 の `ptrdiff.py` を実装している場合のみ意味を持つ）

::: note

**コラム: なぜ `div` が要るのか。**
要素サイズが 2 の冪（4 や 8）なら、割り算ではなく**右シフト**（`srai`）で済む。
除算命令は乗算より数倍遅いので、実際のコンパイラは
「サイズが 2 の冪ならシフト」という最適化を必ず行っている。
B1 のピープホール最適化の練習問題として、
`li a1, 4` + `div a0, a0, a1` を `srai a0, a0, 2` に置き換える規則を書いてみるとよい。
（言語からシフト演算子 `<<`/`>>` そのものは消えたが、`srai` は命令としては
最適化で普通に使われる——ここで言うシフトは言語機能ではなく命令選択の話である。）

:::
