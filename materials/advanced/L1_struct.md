# 構造体の代入 — レジスタに載らないものを運ぶ

## 今日のゴール

`q = p;` のように、構造体をまるごとコピーできるようにする。
ポインタ・フィールドを持つ構造体（`Line` の中の `Point *`）やポインタ経由
（`*dst = *src`）も動くようにする。

## この回の位置づけ

- 言語機能発展シリーズ（選択制）。前提はコマ12（構造体）
- コマ12 の資料が「構造体のネスト、構造体代入、グローバル構造体変数は扱わない」と
  明示的に先送りした宿題の回収
- `mycc.py` は書き換えない。ラッパー `langcc.py`（完成品）が `Assign` の生成だけ差し替える
- 編集するのは `structcopy.py` の2つの関数

::: warning

**引数の値渡し（`f(p)` で構造体を渡す）と戻り値の値渡しは、この回では扱わない。**
どちらも RV64 の呼び出し規約に踏み込む必要があり（16バイト以下はレジスタ2本、
それより大きければ呼び出し側が領域を用意して隠し引数で渡す）、
分量が2倍以上になるためである。発展課題で設計だけ扱う。
いままで通り、関数へはポインタで渡す（`f(&p)`）。

:::

## いまはどうなっているか

```c
struct Point p; struct Point q;
p.x = 3; p.y = 4;
q = p;
return q.x + q.y;     // 7 のはず
```

いまのコンパイラは、これを**エラーにせず、間違った答えを返す**。

ポインタ・フィールド経由のメンバアクセス（`l.a->y`）は、実は既に正しく動く。
`l.a` はただのポインタなので、`->` は「ポインタの指す先の `y` を読む」という、
コマ11までと同じ処理でしかない。
**壊れているのは代入（`m = l` で `l.a`・`l.b` という2本のポインタをコピーする部分）だけ**である。

## なぜ壊れるのか — レジスタに載らない

いままでの代入は、こういう形だった。

```text
左辺のアドレスを求める → 退避
右辺の値を a0 に載せる
a0 を左辺のアドレスへ書き込む
```

「右辺の**値**を a0 に載せる」——ここが構造体では成り立たない。
`Point` は8バイト、`Line` は16バイト、もっと大きい構造体もある。
**レジスタ1本に載らないものは、この方式では運べない。**

いまの実装は、構造体でも同じ道を通って `ld` / `sd` で8バイトだけ写す。
`Point`（ちょうど8バイト）なら偶然動きそうに見えるが、
型サイズの計算がずれて `lw`（4バイト）になり、`y` が写らない。
結果として `q.y` はゴミになる。

## どう直すか — アドレスからアドレスへ

構造体の代入は、**値の移動ではなくメモリのコピー**である。

```text
左辺の「アドレス」を求める   → a1
右辺の「アドレス」を求める   → a0     ← 値ではない
a0 から a1 へ、size バイト写す
```

右辺に `codegen()` ではなく **`codegen_lval()`** を使うのが要点である。
コマ9 で学んだ「rvalue と lvalue」の区別が、ここで効いてくる。
構造体の代入では、**右辺も lvalue として扱う**。

コピーは大きい単位から行う。

```asm
  ld a2, 0(a0)      ;; 8バイトずつ
  sd a2, 0(a1)
  ld a2, 8(a0)
  sd a2, 8(a1)
  lw a2, 16(a0)     ;; 残りが4バイト以上なら4バイト
  sw a2, 16(a1)
  lb a2, 20(a0)     ;; 最後の端数は1バイト
  sb a2, 20(a1)
```

::: note

**これは `memcpy` である。**
いま書いたループは、libc の `memcpy(dst, src, n)` がやっていることそのものである。
実際のコンパイラも、構造体の代入を `memcpy` の呼び出しに変換することが多い
（サイズが小さいときは、いまのように命令を並べて展開する）。
「構造体の代入」という言語機能の正体は、**メモリのコピー**である。

:::

## 代入式の値は何か

C では代入も式なので、`a = (b = c)` のように値を持つ。
構造体の代入の場合、その値は「代入された構造体」である。

レジスタには載らないので、この回では**左辺のアドレス**を `a0` に残しておく。
`p = q = r;` のような連鎖でも、次の代入が `codegen_lval` でアドレスを求め直すので
辻褄が合う。

`assign.c` の「コピー後に元を変えても影響しない」が本質的である。
参照ではなく**複製**であることを、そこで確かめている。

## 発展課題

1. **引数の値渡し**: `int area(struct Point p)` を書けるようにする
   （この言語仕様では struct 値の実引数は不可なので、Core の外に出る設計課題）。
   RV64 の規約では、16バイト以下の構造体はレジスタ2本に分けて渡し、
   それより大きければ呼び出し側がコピーを作ってアドレスを渡す。
   簡易版として「常にコピーを作ってアドレスを渡す」方式を設計してみる
   （libc とやり取りしないなら、それでも動く）
2. **戻り値の値渡し**: `struct Point make(int x, int y)` は
   （こちらも struct 値の戻り値が不可な Core の外に出る設計課題）、
   呼び出し側が領域を用意し、その**アドレスを隠し引数として渡す**方式で実現できる
   （sret と呼ばれる）。なぜ「戻り値を a0 に載せる」では足りないのか
3. **大きな構造体**: 1KB の構造体を代入すると、命令が何百行も並ぶ。
   サイズが一定を超えたら `memcpy` を呼ぶように変える
4. **グローバル構造体変数**: `struct Point origin;` をグローバルに置けるようにする
   （`.bss` のサイズ計算は `_struct_defs` から引ける）
5. **構造体の比較**: C では `p == q` は**書けない**。なぜ代入はできて比較はできないのか

::: note

**コラム: 「値」の大きさが違うということ。**
`int` の代入も構造体の代入も、C の文法上は同じ `=` である。
しかし機械語のレベルでは、片方は1命令、もう片方はコピーのループになる。
**言語が同じに見せているものが、実装では違う**——これはコンパイラを書いて
初めて実感できることの1つである。
値になる大きさをどこまで許すかは言語設計の選択で、
この言語は構造体を「値になる」側に置いた結果、
コンパイラがコピーを生成する義務を負っている。

:::
