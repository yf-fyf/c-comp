今日のゴール

int の演算を 32bit 命令（addw など）で行い、 桁あふれの振る舞いを「ホスト gcc と同じ 32bit 折り返し」に揃える。

いまのコンパイラは何をしているか

コマ8 で「int は4バイト」と決め、lw / sw で読み書きするようにした。 しかし計算のほうは、ずっと64bit命令のままである。

  add a0, a1, a0      # 64bit で足している

RV64 には、同じ演算の32bit版がある。

64bit 版 32bit 版 32bit 版の意味
add addw 下位32bitで足し、結果を符号拡張する
sub / mul / div / rem subw / mulw / divw / remw 同上

w は word（RV64 では32bit）の意味である。 int の計算には、本来こちらを使わなければならない。

何が違うのか

int x;
x = 2147483647;   // int の最大値
x = x + 1;

この言語の仕様（language_spec.md）は、符号付き整数のオーバーフローを 未定義動作（UB）と明記している。規格上は「何が起きてもよい」ということだが、 それでは実装の方針が立たない。そこでこの回では、 「ホスト gcc（および RISC-V の実際の挙動）と同じく、32bitで折り返す」 という具体的な振る舞いを選んで実装する（UB の中で最もよく採用される選択であり、 -fwrapv 相当の挙動と考えてよい）。この方針のもとでは、x は 最小値 -2147483647 - 1 に折り返す。

いまの実装は64bitで計算するので、2147483648 という int に存在しないはずの値がそのまま残る。

int y;
y = 100000 * 100000;   // 折り返す方針では: 1410065408
                        // いまの実装: 10000000000
重要

このずれも、S1 と同じくテストが通ってしまう種類のものである。 講義のテストは小さい値しか使わないので、64bitでも32bitでも同じ答えになる。 大きな値を扱った瞬間に、初めて食い違う。

「小さい入力でテストする」のは正しい習慣だが、 境界値を試さないと見つからないバグがあることも同時に示している。

どう直すか — 命令を書き換える

コード生成のあちこちに散らばった add / sub / mul … を すべて書き直すのは大変である。そこで、出力される命令行を通り道で書き換える。

codegen が emit("  add a0, a1, a0") を呼ぶ
    ↓
narrow(line, ty) が「型が int なら addw に」書き換える
    ↓
実際に出力される

narrow は純粋な文字列変換なので、テストが書きやすい。 ラッパー semcc.py が emit を包んでこれを呼ぶ。

難しいのは「どこを書き換えないか」

素朴に「add を全部 addw にする」と、コンパイラは壊れる。

命令 用途 32bit にすると
add a0, a1, a0 x + y（int の足し算） 正しい
add a0, a1, a0 p + i（ポインタ演算） アドレスが壊れる
addi a0, s0, -24 変数のアドレス計算 アドレスが壊れる
addi sp, sp, -16 スタックの確保 sp が壊れる

アドレスは64bitである。同じ add でも、 「何を計算しているか」で扱いが変わる。

そこで2つの仕掛けを使う。

  1. addi は対象外にする — アドレス計算専用と割り切る （このコンパイラは int の加算に addi を使わない）
  2. 型コンテキストを見る — いま生成している式の型が int / char のときだけ書き換える

2つ目はラッパーが用意する。codegen を包んで、 「いま生成中のノードの型」をスタックで持ち回り、emit のときに参照する。

補足

入れ子のアドレス計算に注意。 int *p; に対する s = s + p[i] を考える。外側の + は int だが、 その中の p[i]（*(p + i) の略記）はアドレス計算（base + i*4）である。 外側の型を内側にも適用してしまうと、アドレスが32bitに切り詰められて落ちる。

ラッパーは、算術ノード以外では型を None にして積み直すことでこれを防いでいる。 実際に作る途中でこの罠を踏み、f11_ptr_arith.c が SIGSEGV で落ちた ——「型は式ごとに違う」ことを、身をもって確かめられる箇所である。

発展課題

  1. unsigned を考える: unsigned int があれば divu / remu が要る。 Core プロファイルに unsigned がないのはなぜか、あると何が増えるか
  2. long との違い: C の long は64bitである。 仕様に long を足すとしたら、narrow はどう変わるか
  3. char の扱い: char は1バイトだが、計算は int に格上げされる（整数拡張）。 いまの実装は char も32bitで計算しているが、これで正しいか
  4. 比較は大丈夫か: slt は64bit比較だが、32bitで符号拡張された値同士なら 正しく比較できる。なぜそう言えるか説明する
  5. B1 と組み合わせる: 定数畳み込み（B1）の to_i64 は64bitで丸めている。 int の式なら32bitで丸めるべきではないか。両者の整合を取る
補足

コラム: なぜ RV64 に32bit命令があるのか。 RISC-V は64bit CPU だが、C の int が32bitであることを前提に、 32bit演算を1命令でできるようにしてある（addw など）。 これがないと、足すたびに「下位32bitを取り出して符号拡張する」処理が余分に要る。 言語の都合が命令セットの設計に影響している例である。 x86-64 も同じ理由で、32bit レジスタ名（eax）での演算が用意されている。
