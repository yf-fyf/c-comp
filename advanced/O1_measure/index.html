今日のゴール

最適化の効果を測る物差しを2つ作る。 静的命令数（出力に命令が何個あるか）と動的命令数（実行時に何回実行されたか）である。 この2つが桁違いに食い違うことを、自分のコンパイラの出力で確かめる。

項目 内容
必須の前提 コマ15（完成した final/mycc.py）
推奨の前提 —
改変しない mycc.py、scaffold/、optcc.py
編集する measure.py
完了条件 check.py の全 Step が PASS になり、golden.py がベンチマークの正しさと静的／動的の表を報告する

備考 最適化発展シリーズの第1回。以降のすべての回が、この物差しとベンチマーク集 bench/ を使う。O 系列の命令数の基準表もこの回に置いてある

以降のすべての最適化の回が、この回で作った物差しを使う。 最初に作る理由がこれである。

なぜ測るのか

B1（定数畳み込みとピープホール）では「命令数が16%減った」と報告した。 しかし、その16%は本当に速くなったのだろうか。

int main() {
    int i; int s;
    s = 0;
    for (i = 0; i < 200; i = i + 1) { s = s + i; }
    return s % 256;
}

このプログラムが出力するアセンブリは70命令ほどである。 しかし、実行される命令は 7,840個ある。ループ本体が200回繰り返されるからである。

つまり、ループの外にある命令を1個消しても、ほとんど速くならない。 逆に、ループの中の1命令を消すと200命令分速くなる。 「命令数が減った」だけでは、どちらの話をしているのか分からない。

2つの物差し

静的命令数 動的命令数
何を数えるか アセンブリに書かれた命令の個数 実行時に実行された命令の回数
測り方 テキストを数える qemu で実行を追う
反映されるもの コードサイズ 実行時間
ループの影響 受けない 大きく受ける

どちらも意味がある。組み込み機器ではコードサイズ（静的）が制約になるし、 実行速度が問題なら動的を見る必要がある。

動的命令数の測り方

qemu には、実行した命令を記録する仕組みがある。

qemu-riscv64 -one-insn-per-tb -d exec,nochain ./prog
  • -d exec は、実行のたびに Trace ... という行を出す
  • 既定では複数命令をまとめた単位（トランスレーションブロック）ごとに出るので、 -one-insn-per-tb で1命令 = 1行にそろえる

出てくる行はこの形をしている。

Trace 0: 0x7fe594000100 [003411ef/000000000001038c/0202c078/00000201] _start
                                  ↑ 実行した命令のアドレス(PC)

落とし穴: libc が混ざる

そのまま数えると、loop_sum は 144,220命令になる。 自分のプログラムは7,840命令なので、95%が libc の起動処理である。

_start(libc) → 環境変数の準備 → ロケール初期化 → ... → main → ...

これでは自分の最適化の効果が埋もれてしまう。そこで、 自作した関数のアドレス範囲だけを数える。

  1. アセンブリの .globl から自作関数の名前を集める
  2. nm で実行ファイルの各シンボルのアドレスを引く
  3. Trace 行の PC がその範囲に入っているものだけ数える

これで 144,220 → 7,840 に絞り込める。

補足

なぜログをファイルに書かないのか。 -D file でログをファイルに落とすこともできるが、 今回の例でも13MBになる。数百万命令のベンチマークでは数GBに達する。 スケルトンでは subprocess.Popen でパイプから1行ずつ読みながら数えるようにしてある。 ディスクを使わず、メモリにも溜めない。

ベンチマーク集

bench/ に5本用意した。以降の回でも同じものを使う。

ベンチマーク 特徴
loop_sum.c 単純なループ
matmul.c 3重ループ、malloc 領域へのポインタアクセスが多い
fib_rec.c 再帰、関数呼び出しが多い
bubble.c malloc 領域へのポインタアクセスの入れ替え、分岐が多い
strops.c 文字列走査、char アクセス

いずれも .ans を持ち、test_runner.py で正しさを確認できる。 最適化した結果が正しいことの確認にも、そのまま使う。

実装

Step 実装対象 内容
1 count_static アセンブリの行を数える（ラベル・ディレクティブ・コメントは除く）
2 count_dynamic の数え上げ Trace 行を読み、PC で絞り込んで数える

nm の呼び出し（our_symbol_ranges）と範囲判定（in_ranges）、 qemu の起動はスケルトンで用意してある。

python3 golden.py       # 5本のベンチマークを両方の物差しで測る

テスト

python3 check.py     # 数え上げの単体テスト(未実装は SKIP)
python3 golden.py    # ベンチマークの正しさ + 静的/動的の表

check.py の後半は、同じプログラムの反復回数だけを変えて測り、

  • 動的命令数はほぼ2倍になる
  • 静的命令数はほとんど変わらない

ことを確かめる。物差しが正しく機能していることの検証である。

素の出力は何でできているか

素の 1,183命令のうち 587命令（49.6%）が、コマ2 以来の push/pop の往復 （addi sp, sp, -8 / sd a0, 0(sp) / ld a1, 0(sp) / addi sp, sp, 8）である。 式の途中結果をメモリに逃がすたびに4命令を払っている勘定で、 出力のおよそ半分が値の往復に消えている。 これを減らすのが O4（変数をレジスタへ）と B2（式の途中結果をレジスタへ）の主題である。

# 自分の出力でも数えてみる（matmul は 242/453）
python3 optcc.py --passes '' O1_measure/bench/matmul.c \
    | grep -cE 'addi sp, sp, -?8$|(sd|ld) a[0-9]+, 0\(sp\)$'
補足

この表の数字は「教員の実装で測った値」である。 自分の mycc.py の書き方によって素の命令数は変わるので、 列どうしの比（何%減ったか）を見て、絶対値の一致は求めなくてよい。 動的命令数は qemu のバージョンによっても数命令ぶれる （libc の起動処理の命令数が変わるため、上の「144,220命令」も同様である）。

発展課題

  1. B1 と比べる: advanced/B1_fold_peephole/foldcc.py でコンパイルしたものを 同じ物差しで測り、静的16%減が動的では何%減になるか調べる
  2. 関数ごとに測る: いまは自作コード全体をまとめて数えている。 nm の情報を使えば関数ごとに分けられる。どの関数が重いか（プロファイル）が分かる
  3. 実行時間と比べる: time qemu-riscv64 ./prog の実測時間と動的命令数を比べる。 命令数に比例するか。しないとすればなぜか（メモリアクセスの速さの違い）
  4. 命令の種類別に数える: ロード/ストア、分岐、算術に分けて数える。 最適化の狙いどころが見えてくる
補足

コラム: 測らない最適化は当てにならない。 「この書き方のほうが速い」という直感は、しばしば外れる。 現代の CPU は分岐予測・キャッシュ・命令の並列実行を行うので、 命令数が減っても速くならないこと、増えても速くなることがある （O7 で扱うループ回転は、静的命令数をまったく変えずに動的命令数を減らす例である）。 だからこそ、最適化の議論は必ず測った数字から始める。 この回で作った物差しは、以降のすべての回で「本当に良くなったのか」を答えるために使う。
