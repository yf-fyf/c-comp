# AI モデル利用方針

この文書は、教材の品質を保ちながら AI を過不足なく利用するための基本方針を定める。
契約プラン、料金、個人の利用上限には依存せず、モデルの能力と作業の難しさを対応させる。

---

## 基本原則

1. 通常の制作・実装・レビューには Sonnet 相当のモデルを使用する。
2. 単純な検索や定型確認には Haiku 相当のモデルも使用できる。
3. 最上位モデルは、通常モデルでは判断が難しい作業と、複数エージェントを束ねる役割に限定する。
4. モデルを上げる前に、対象範囲、期待結果、確認方法を明確にする。
5. 制作と独立レビューは別セッションで行い、レビューへ制作時の判断を持ち込まない。
6. 実行していないコマンドを成功したものとして扱わない。
7. AI の提案を公開判断とせず、最終判断はメンテナが行う。

## 作業ごとの選択

| 作業 | 基本選択 |
|------|----------|
| 教材文面の編集、通常のコード修正、対象テストの実行 | Sonnet / medium |
| ファイル特定、定型的な差分確認、単純な調査 | Haiku または Sonnet / low |
| 通常の教材レビュー、公開前確認 | 新規セッションの Sonnet / medium |
| 言語仕様、ABI、複数実装をまたぐ難しい不整合 | 必要に応じて最上位モデル |
| 高難度の最終技術監査 | 必要に応じて最上位モデル |

次のいずれかに該当するとき、最上位モデルの使用を検討する。

- Sonnet で調査しても原因または判断材料を十分に絞れない
- 言語仕様、実装、教材の複数層を同時に整合させる必要がある
- 複数の実装言語や実行環境にまたがる根本原因を判断する
- 誤判断による広範囲な手戻りが見込まれる
- 長時間の自律的な調査と検証が作業の中心になる

モデルを上げる理由がなくなった後の実装、文面調整、限定的な再確認は通常モデルへ戻す。

## 複数エージェントで分担する場合

大きな工程を複数のサブエージェントに分けて進めるときは、モデルを難易度だけでなく
**役割**でも割り当てる。

| 役割 | 仕事 | 基本選択 |
|------|------|----------|
| オーケストレータ | 作業の分割、起動順の決定、報告の読解、判断の裁定。**自分ではファイルを編集しない** | 最上位モデル |
| ワーカー（設計を伴う） | 新しい教材の執筆、新しい実装の設計 | 必要に応じて最上位モデル |
| ワーカー（指示どおりの改修） | 変更箇所が特定済みの修正、テスト実行と軽い自己修正 | Sonnet / medium |
| レビュアー | 検証の再現と指示との突き合わせ。担当ワーカーとは別セッション | Sonnet / medium |
| スイーパー | 検索による残存確認、定型的な一括置換 | Haiku |

オーケストレータに最上位モデルを使うのは、判断の誤りが全ワーカーへ波及する位置にあるためであり、
「最上位モデルは判断が難しい作業に限定する」原則の範囲内として扱う。
逆に、**最上位モデルをワーカーとして常用しない**。1 エージェントには 1 件の作業だけを渡す。

各エージェントの成果物は、決められた様式の作業レポートに集約する。レポートには実施日、
担当モデル、作業開始時のコミット、完了したかどうか、測定を伴う場合は測定環境を必ず記録する。
後から結果の根拠を追跡できるようにするための最低限の欄である。

## 複数の AI サービスを併用する場合

本コースでは Claude Code を主に使い、必要に応じて別系統の AI（OpenAI Codex）を併用する。
二系統を使う目的は利用枠の分散ではなく、**同じ判断を別の実装・別の視点から確かめる**ことにある。

役割は次のように分ける。

| 作業 | 基本選択 |
|------|----------|
| 学習目標、前提、完了条件、教材の順序の決定 | 主系統（併用しない） |
| 日本語の説明品質、ヒントの量、学習者経路の判断 | 主系統（併用しない） |
| 言語仕様、ABI、公開範囲の判断 | 主系統（併用しない） |
| 計画・着手順への第二意見 | 別系統（読み取りのみ）→ 採否は主系統とメンテナ |
| コード中心の独立レビュー | 別系統（読み取りのみ）→ 教材上の重大性の判断は主系統 |
| ビルドエラー・テスト失敗の原因の切り分け | 別系統（読み取りのみ） |
| 同じ問題に対する別実装の提示 | 別系統（読み取りのみ）。採用する場合は主系統が書き直す |
| 既知の方針に沿う定型的な複数ファイル修正、リネーム、同期 | どちらでもよい |

併用時の規律は次のとおり。

- 目的、対象、完了条件を主系統で短く確定してから別系統へ渡す。同じ全体調査を二重にさせない。
- 別系統の指摘は第二意見であって決定ではない。既に確定した方針と食い違う指摘が出た場合は、
  再確認するかどうかをメンテナが判断する。
- 書き込みを伴う委譲は、対象パスと完了条件が明確で、同じ作業コピーを他方が編集していない場合に限る。
  委譲後は差分と対象テストを確認する。
- 会話履歴をまるごと別サービスへ移す機能は、次節の「渡さない情報」を含む会話では使用しない。

### 外部サービスへ渡さない情報

どの AI サービスを使う場合も、次は渡さない。判断に迷う場合は渡さない。

- 完成解答、隠しテスト、品質記録。これらは非公開の設計リポジトリだけで扱う。
- 学習者の氏名、提出物、進捗、受講記録などの個人情報と授業記録。
- ホスト名、IP アドレス、絶対パス、認証情報などの環境固有の識別子。

公開リポジトリの教材、仕様、実装、テスト、設計方針は渡してよい。
非公開側の情報を渡す必要が生じたときは、まず公開側の情報だけで問い合わせを組み立て直せないかを
検討する（例: 解答そのものではなく、解答が満たすべき条件を渡す）。

## セッションの分離

次の場合は、既存の長い会話を継続せず新しいセッションを使用する。

- 対象となる教材系列または機能が変わる
- 制作から学習者経路レビューへ移る
- 学習者経路レビューから技術・実行レビューへ移る
- 前の作業で読んだファイルや判断が次の作業に不要である

長期の仕様設計など、過去の決定が作業の前提になる場合だけ同じセッションを継続する。
継続時も、対象ファイル、確定事項、未完了事項を明確にしてから次の作業へ進む。

## 調査範囲

- 最初に対象の教材、ディレクトリ、失敗したコマンドを指定する。
- リポジトリ全体の探索は、対象範囲だけでは原因を判断できない場合に限る。
- 生成物や依存パッケージではなく、原稿、ソース、生成手順を優先して確認する。
- 大量のログは失敗箇所とその前後へ絞ってから AI に渡す。
- テストは変更範囲に対応する最小のものから実行し、必要な場合だけ回帰範囲を広げる。

## レビュー

教材レビューの基準と記録方法は `design/quality_guide.md` に従う。
学習者経路レビューでは `workbook/` だけを対象とし、技術・実行レビューでは指定された原稿、配布物、仕様を照合する。
完成解答、品質記録、隠しテストは `../c-comp-design/` だけで扱い、公開リポジトリへ移さない。
