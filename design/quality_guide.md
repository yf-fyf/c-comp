# 教材品質管理ガイド

通常回・advanced回の教材を作成、公開、改善するときの最小限の品質管理手順を定める。
メンテナとAIが共同で利用し、日常的に継続できることを優先する。

このガイドの目的は、教材を細かく採点することではない。
学習者の進行を妨げる重大な問題を公開前に見つけ、利用後の改善材料を残すことである。

教材系列ごとの記録には Private リポジトリ `../c-comp-design/teacher/quality/template.md` を使用する。

---

## 1. 運用原則

1. 記録は教材系列単位で作る。
2. 公開前に、学習者経路と技術・実行の2回だけAIレビューを行う。
3. AIの指摘はメンテナが確認し、公開判断はメンテナが行う。
4. 公開を妨げる問題と、将来の改善候補を分ける。
5. 実際の利用で得た観察を、次の改善に利用する。
6. 運用上の効果が確認できない項目は増やさない。

完成解答や自動テストは必須ではない。
ただし、学習者とメンテナが到達を判断できる完了条件は必須とする。

---

## 2. 記録単位

通常回はPhase単位、advanced回は回IDの頭文字（カテゴリ）単位で記録する。
記録は `../c-comp-design/teacher/quality/template.md` から作成し、
`../c-comp-design/teacher/quality/records/<series-id>.md` に保存する。

記録名の例: `phase-0` / `phase-1` / `phase-2` / `advanced-F` / `advanced-O`

系列に含まれる教材すべてを同時に公開する必要はない。
記録には、各構成教材が今回の公開対象かどうかを明示する。

### 系列と構成教材の状態

| 状態 | 意味 |
|------|------|
| `Draft` | 制作または修正中 |
| `Ready` | 必須確認を終え、メンテナが公開可能と判断した |
| `Validated` | 実際の利用後に改善要否を確認した |
| `Needs revision` | 公開または継続利用を止める問題がある |

系列を`Ready`にできるのは、今回の公開対象に含まれる構成教材がすべて`Ready`または`Validated`である場合とする。
公開対象の構成教材が一つでも`Needs revision`になった場合は、修正または公開対象からの除外まで系列も`Needs revision`にする。

---

## 3. 必須品質基準

公開対象について、次の5点だけを必須確認とする。

| 観点 | 確認すること |
|------|--------------|
| 目標と完了条件 | 学習目標、前提、完了条件が明確である |
| 学習者経路 | 学習者向け資料だけで開始し、次の作業を判断できる |
| 技術的正確性 | 中心的な説明、コード、期待結果が正しい |
| 実行可能性 | 記載されたビルド、テスト、確認手順が動く |
| 公開範囲 | 完成解答の意図しない混入や不要な内部情報がない |

難しいこと、長いこと、他教材に依存すること、自動テストがないことは、それだけでは品質上の問題ではない。

指摘は次の2種類に分ける。

| 種別 | 扱い |
|------|------|
| `Blocker` | 解消または公開対象から除外するまで`Ready`にしない |
| `Improvement` | 公開を妨げない。必要性と優先度をメンテナが判断する |

---

## 4. 標準ワークフロー

### Step 1: 系列の基本情報を記述する

対象学習者、学習目標、前提、完了条件、構成教材、今回の公開対象を記録する。
学習目標は「理解する」だけで終わらせず、実装、説明、比較、実験、デモなど観察可能な形にする。

制作中に実行した確認は「制作時確認」として区別して書く。
制作時確認はAIレビューの代替にならない。

### Step 2: 学習者経路をAIレビューする

学習者向け配布物（`workbook/` 内）だけをAIに見せる。
レビューは、教材を制作した会話とは別の、制作文脈を持たないセッションで行う。

確認する内容:

- どこから開始するか分かる
- 次に読む、編集する、実行する場所が分かる
- 未記載の前提がない
- 失敗時に最初の調査を始められる
- 完了条件が学習者から見える

### Step 3: 技術・実行をAIレビューする

教材原稿（`materials/`）、学習者向け配布物（`workbook/`）、仕様を照合する。
このレビューも、制作文脈を持たないセッションで行う。
実行を伴う確認は、対象系列と無関係な作業中の変更を含まない隔離コピーで行うことを推奨する。

確認する内容:

- 中心的な技術説明と期待結果
- 原稿と配布物の対応
- 記載されたビルドとテスト
- 未完了を成功扱いする経路

AIが実行していないコマンドを、成功したものとして扱わない。

### Step 4: Blockerを処理する

AIの指摘をメンテナが確認する。
誤った指摘は採用せず、採用した`Blocker`だけを修正または公開対象から除外する。

`Improvement`は、効果が見込める場合だけ対応する。
網羅性のために説明、テスト、記録を増やさない。

修正後は、変更した範囲について学習者経路または技術・実行を再確認する。

### Step 5: メンテナがReadyを判断する

リビジョン、公開対象、実行したコマンドと結果、`Blocker`修正後の確認結果、未解決`Blocker`がないこと、判定者と日付を記録する。
公開対象に未解決`Blocker`がある場合、系列を`Ready`にしない。

### Step 6: 利用後に短く記録する

実際に観察できたものだけを記録する。

- 学習者が停止した場所
- 追加説明が必要だった場所
- 完了条件を適用できたか
- 次回直すこと

改善要否を確認できたら`Validated`にする。
継続利用を止める問題が見つかったら`Needs revision`にする。
個人を特定できる情報は記録しない。

## 5. 簡易レビュー

既に`Ready`または`Validated`の教材系列に対する、意味と動作を変えない変更だけに使用する。

対象例: 誤字脱字、体裁、意味を変えない言い換え、原稿が変わっていない状態での生成物の再生成。

次は標準ワークフローを使用する。

- 学習目標、前提、完了条件の変更
- 課題手順やTODOの変更
- コード、テスト、期待結果の変更
- 依存関係の変更
- 学習者の解法や判断に影響する説明、ヒント、例の追加

簡易レビューでは次だけを行う。

1. 意味と動作が変わらないことを差分で確認する。
2. 必要なリンク確認またはサイト生成（`make site && make check-links`）を行う。
3. 実施した確認と状態維持の判断を変更履歴へ1行記録する。

### 共有ファイルの変更

`workbook/scaffold/`、`workbook/final/`、`workbook/docs/` など複数の系列が依存するファイルを変更した場合は、
依存する各系列について再確認の要否を判断する。

---

## 6. Advanced教材の補足

advanced教材では、5つの必須品質基準に加えて次を確認する。

- 必須前提と推奨前提を区別する
- 他のadvanced教材への依存を明示する
- 複数コマの場合は途中成果または再開地点を示す
- 一斉説明なしで開始できる
- 未完でも試行、失敗、測定、判断を説明できる

難しい教材を一律に易しくしない。
意図した難しさと、未記載前提や壊れた手順による偶発的な難しさを区別する。

## 7. このリポジトリでの前提

| パス | 役割 |
|------|------|
| `materials/sessions/` | 通常回の資料のMarkdown原稿 |
| `materials/advanced/` | advanced教材の資料のMarkdown原稿 |
| `materials/figures/` | 図のTikZソースと生成SVG（`ast/` は生成物） |
| `workbook/` | 学習者向け配布物。この範囲だけで演習を実施する |
| `workbook/sessions/` | 通常回のREADME、starter、テスト |
| `workbook/advanced/` | advanced教材のREADME、starter、テスト（1トピック=1ディレクトリ） |
| `workbook/porting/` | C移植・セルフホストトラック |
| `workbook/docs/language_spec.md` | Coreプロファイルの言語仕様 |
| `workbook/docs/getting_started.md` | 学習者向け進め方ガイド |
| `design/curriculum.md` | 教育方針と全体設計 |
| `../c-comp-design/teacher/answers/` | Private リポジトリの完成解答。存在しない教材もある |
| `../c-comp-design/teacher/quality/` | Private リポジトリの教材品質記録（`template.md` と `records/`） |

完成解答・品質記録・隠しテストはこの公開リポジトリに置かず、
Private リポジトリ `../c-comp-design/` だけで管理する。

監査では、対象外の既存変更を修正、削除、巻き戻ししない。
メンテナの許可なくcommitしない。

### 主なビルドコマンド

リポジトリルートから実行する。

```bash
make site          # 資料サイトを .site/ に生成
make check-links   # 内部リンク切れを検査
```

### 主なテストコマンド

通常回は`workbook/`から実行する。

```bash
python3 scaffold/test_runner.py sessions/<session-id>
python3 scaffold/test_runner.py
```

advanced教材は各topicディレクトリから、READMEに記載されたコマンドを実行する。

```bash
python3 check.py
python3 golden.py  # 存在し、READMEで指定されている場合
```

教材によって専用コマンドがあるため、上記だけで完了と判断せず、対象READMEを確認する。

## 8. AIレビューの出力形式

2回のAIレビューでは、次の短い形式を使用する。

```text
Blockers:
- 最大5件。ファイルと行番号、学習者への影響、最小修正を記載する。

Improvements:
- 最大3件。公開を妨げない改善だけを記載する。

Commands:
- 実行したコマンドと結果を記載する。

Not verified:
- 確認できなかったことを記載する。

Recommendation:
- Ready または Needs revision
```

問題がない場合も、確認範囲と未確認事項を記載する。

`Recommendation`はAIによる推奨であり、メンテナの`Ready`判定そのものではない。
最終判断はStep 5でメンテナが行い、記録には推奨と判定を区別して書く。

## 9. リポジトリ専用AIプロンプト

### 9.1 学習者経路レビュー

```text
この教材リポジトリの教材を、学習者経路という観点でレビューしてください。読み取り専用で調査し、ファイルを変更しないでください。

対象系列: <series-name>
今回の公開対象: <student-facing paths under workbook/>
対象学習者の前提: <prerequisites>
完了条件: <completion criteria>

参照してよいのは、原則としてworkbook/内の学習者向け配布物だけです。Private リポジトリ `../c-comp-design/`、完成解答、教材別品質記録は参照しないでください。学習者が資料サイトを読む想定の場合、materials/のMarkdown原稿を学習者向け資料の代わりにしないでください。

次を確認してください。
- 開始地点が分かるか
- 次に読む、編集する、実行する場所が分かるか
- 未記載の前提がないか
- 失敗時に最初の調査を始められるか
- 完了条件が学習者から見えるか

難しいことや複数教材への依存自体を問題にしないでください。意図した難しさと、記述不足による偶発的な難しさを区別してください。

出力はBlockers（最大5件）、Improvements（最大3件）、Commands、Not verified、Recommendation（ReadyまたはNeeds revision）だけにしてください。各指摘にはファイルと行番号、学習者への影響、最小修正を含めてください。
```

### 9.2 技術・実行レビュー

```text
この教材リポジトリの教材を、技術的正確性と実行可能性という観点でレビューしてください。監査対象以外の既存変更を修正、削除、巻き戻ししないでください。ファイルは原則として変更せず、生成物を作る検証は許可された作業環境でだけ実行してください。commitは行わないでください。

対象系列: <series-name>
今回の公開対象: <student-facing paths under workbook/>
原稿: <paths under materials/>
関連仕様: <paths, normally workbook/docs/language_spec.md and design/curriculum.md>
メンテナ用資料: <paths under ../c-comp-design/, if any>
完了条件: <completion criteria>

materials/の原稿、workbook/の配布物、関連仕様、メンテナ用資料を照合してください。次を確認してください。
- 中心的な技術説明、コード、期待結果が正しいか
- 原稿、README、starter、テスト、生成されたページが矛盾していないか
- READMEに記載されたビルド、テスト、確認手順が動くか
- SKIPや未実装を成功として扱う経路がないか
- 完成解答や不要な非公開情報がworkbook/へ混入していないか

実行していないコマンドを成功したと表現しないでください。仕様外の内容は、適切な一次資料または明示された教育上の定義と照合してください。

出力はBlockers（最大5件）、Improvements（最大3件）、Commands、Not verified、Recommendation（ReadyまたはNeeds revision）だけにしてください。各指摘にはファイルと行番号、学習者への影響、最小修正を含めてください。
```

### 9.3 簡易変更レビュー

```text
この教材リポジトリの教材変更が簡易レビューの対象か確認してください。ファイルは変更しないでください。

対象差分: <diff or revisions>

簡易レビューを使えるのは、意味と動作を変えない変更だけです。学習目標、前提、完了条件、課題手順、TODO、コード、テスト、期待結果、依存関係、学習者の解法に影響する説明が変わる場合は標準ワークフローを推奨してください。

次だけを返してください。
- Decision: Quick review または Standard review
- Reason: 判断理由
- Minimum checks: 必要な差分確認、リンク確認、サイト生成など
- Not verified: 確認できなかったこと
```

## 10. このガイドの改善

このガイド自体も、運用しながら改善する。

- 記入されない項目は削除を検討する
- 判断に使われない記録は必須にしない
- 繰り返し発生する重大問題だけを新しい確認項目にする

網羅性より、継続して利用できることを優先する。
