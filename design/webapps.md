# 補助ウェブアプリ 企画書

教材のウェブ公開に合わせて併設する、学習支援用のウェブアプリの設計方針とアプリ案をまとめる。

この文書は**なぜそう作るか**を決めるためのものである。
コマ一覧・言語仕様・実行手順は `workbook/` 側を出典とし、ここでは再掲しない。

状態: **A1（AST ビジュアライザ）と A2（RV64 シミュレータ）を実装済み**。
実装は [`../web/`](../web/README.md)、ビルドは `make web`、
検証は `make web-test`（黄金テスト + vitest）と `make sim-test`（qemu 照合）。
A3 以降は未着手。

---

## 1. 目的と原則

資料 PDF の中で静止画とコマンド例になっている部分を、ブラウザ上で手を動かせる形に置き換える。
とくに handout の各回が冒頭で行う「AST を確認する」ステップと、
[`workbook/docs/debugging.md`](../workbook/docs/debugging.md) が扱う「動かないときの切り分け」を対象にする。

設計原則は次の4つとする。

| 原則 | 内容 |
|------|------|
| **資料と一致する** | 画面に出す AST は handout の図・S 式と同じ木にする。見た目が違うと学習者は別物だと判断する |
| **環境構築の前に触れる** | Docker も qemu も無しで動く。コマ1 に着手する前でも AST を眺められる状態を作る |
| **教材を単一の出典にする** | プリセット入力は `workbook/**/tests/*.c` からビルド時に生成する。アプリ側にサンプルを手書きしない |
| **答えを先に見せない** | 参照実装の出力を表示するモードは、既定で隠し、明示操作と注意書きを挟む |

想定する使われ方は「学習者の自習」と「授業中の教員デモ」の両方である。
後者のために、プリセットからの即起動・大きな文字・ステップ実行・
操作列と状態表示が常に画面内にあることの4点を UI 要件として先に固定する。
ステップ実行が主操作なので、押すたびに操作ボタンが画面外へ流れる状態は不可とする。

## 2. アプリ案カタログ

優先度順に並べる。第1優先の A1〜A3 が MVP で、以降はその基盤の上に1つずつ足せる。

### 2.1 第1優先（基盤 + 効果が大きい）

| ID | アプリ | 対象 | 内容 |
|----|--------|------|------|
| A1 | AST ビジュアライザ | コマ1・2 と、全回の「AST を確認する」 | C ソース → トークン表 / AST 木（SVG）/ S 式。ノードを指定すると対応するソース範囲がハイライトされる。部分木の折り畳み。`a > b` が `(lt b a)` に正規化されることの注釈を出す。JSON / DOT の直列化は内部 API と検証用に残すが画面には表示しない |
| A2 | RV64 シミュレータ | コマ3 以降すべて | アセンブリを貼ってステップ実行する。レジスタ、スタックメモリ（フレーム境界と `s0` 相対オフセット付き）、`.data`、終了コード、`printf` 出力を並べて表示する。逆ステップとブレークポイントを持つ |
| A3 | codegen ステッパ | コマ3・4 以降 | AST のノードを選ぶと、そのノードが出した命令列がハイライトされる。`materials/figures/03_eval_vs_codegen.tex` の対話版 |
| A4 | eval_ast ステッパ | コマ2 | 再帰的な訪問順と、戻り値が木を上がっていく様子をアニメーションする。A1 の木描画をそのまま使う |

A2 は `debugging.md` の症状表を正面から狙う。次の教育的チェックを組み込む。

- `call` の直前に `sp % 16 != 0` になっていたら警告する
- `ra` が退避されないまま上書きされたら警告する
- 未初期化のスタック領域を読んだら警告する
- 現在フレームの外を触ったら警告する

> **実装時の記録（2026-07）**: 上記に加えて、終了コードが 0〜255 に収まらない場合と、
> 呼び出しをまたいで `a1`–`a7` を読んだ場合（caller-saved の取り違え）も検出する。
> 症状表の8行のうち6行に対応した。警告は停止させず、該当行と症状表の文言を添えて出す。
>
> 入力は**アセンブリのみ**とした。学習者が自分の `mycc.py` の出力を貼る使い方に絞れば
> 答えの流出が構造的に起きない。ブラウザ内で C をコンパイルする案は A3 へ回す。
>
> プリセットは二段構えにした。`web/examples/asm/` の手書きサンプル（1ファイル1概念。
> 不具合例を含む）を既定で見せ、参照実装の出力は「解答例を見る」を押して
> 注意書きに同意したときだけ一覧に加える（5-2 と同じ扱い）。
>
> 暴走ガード（既定100万命令）は必須だった。参照実装のコマ10に実際に無限ループを起こす
> 不具合があり、これが無いとブラウザが固まる。

副産物として動的命令数のカウンタが手に入る。これは O1（最適化の測り方）と
D3（最適化の before/after 比較）がブラウザで完結することを意味する。

## 3. 実装方針

### 3.1 責務の分割

**教材の言語仕様に依存する判断は OCaml、表示とターゲット環境の模倣は TypeScript** とする。

| 層 | 言語 | 担当 |
|----|------|------|
| 言語処理コア `web/core/` | **OCaml → WebAssembly** | 前処理 / 字句解析 / 構文解析 / AST の直列化（S 式・DOT・JSON）/ 型計算（`sizeof`・struct メンバ offset）。将来: 再帰下降トレース（C3）・CFG 構築（D1）・型検査（Q1） |
| フロントエンド `web/app/` | **TypeScript** | UI 全般 / AST 木の SVG 描画 / エディタ / 状態管理 / **RV64 シミュレータ** / ステッパの演出 / 検索・進捗などの小物 |

RV64 シミュレータを TypeScript 側に置く理由は3つある。

1. これは言語処理ではなく**ターゲット環境の模倣**であり、上の分割規則に従う。
   入力のアセンブリは行単位で読めるので、構文解析器を必要としない
2. ステップ実行・逆ステップ・ブレークポイントは、1命令ごとに細かい状態を UI へ渡す。
   Wasm 境界を毎ステップ跨ぐのは不利で、状態スナップショットによる逆実行も TypeScript 側の方が素直に書ける
3. 64bit 整数を扱う。OCaml のネイティブ `int` は 63bit なので `Int64` の箱入り演算が必要になるが、
   JavaScript の `BigInt` は 64bit をそのまま表現できる

### 3.2 言語処理コアの実装候補

**OCaml + wasm_of_ocaml** を採る。

| 案 | Wasm 化 | 既存資産の再利用 | 配信サイズ / 起動 | 評価 |
|----|---------|------------------|-------------------|------|
| **① OCaml + wasm_of_ocaml（js_of_ocaml 6 系）** | Wasm-GC を直接出力。dune の `(modes js wasm)` で JS 版も同時に得られる | `workbook/ocaml/support/` の ocamllex + menhir フロントエンドをそのまま使う | 数百 KB・即起動 | **◎ 採用** |
| ② OCaml + js_of_ocaml のみ | JS 出力（Wasm ではない） | 同上 | 最小 | ○ ①のフォールバックとして併用する |
| ③ F# + Fable / Blazor WebAssembly | Fable は JS 出力。Blazor は .NET ランタイムごと Wasm 化（数 MB） | なし。フロントエンドを書き直すことになる | 重い | △ |
| ④ Haskell + GHC wasm32-wasi backend | GHC 公式の Wasm バックエンド | なし | 1〜3 MB + ツールチェーンが重い | △ |
| ⑤ ReScript / Melange | JS のみ | なし | 最小 | △ Wasm 化の要件を満たさない |
| ⑥ Rust + wasm-bindgen | ツールチェーンは最良 | なし。Python・OCaml に次ぐ**3つ目の言語処理実装**が増える | 小 | ○ ただし保守コスト増 |

①を採る理由は次の4点である。

- 教材はすでに OCaml 参考実装を配布している。**言語処理の実装を新しく増やさずに済む**のはこの案だけである
- ウェブアプリが OCaml 実装を常時動かすことになるので、**参考実装が腐らない**。
  現状、OCaml 版のパーサが Python 版と同じ木を作ることを確かめる仕組みは無い
- Pyodide で Python スキャフォールドをそのまま動かす案（約 10 MB のダウンロード）に比べ、初回ロードが桁違いに軽い。
  授業中のデモでも自習でも効く
- `(modes js wasm)` で同一ソースから Wasm と JS の両方が出るので、
  Wasm-GC 非対応ブラウザへのフォールバックが構成だけで解決する

> **実装時の記録（2026-07）**: opam の `binaryen-bin.119` がビルドできず
> wasm_of_ocaml を導入できなかったため、当面は案②（js_of_ocaml のみ）で運用している。
> release ビルドで約 210 KB（gzip 58 KB）と案①の想定サイズに収まっており、
> binaryen が導入できたら `web/core/js/dune` の `(modes js)` を `(modes js wasm)` に
> 変えるだけで案①へ移行できる（[`../web/README.md`](../web/README.md)）。

### 3.3 コアと UI の境界

Wasm 境界は**文字列を渡して JSON 文字列を受け取る**形に限定し、複雑な値を跨がせない。
OCaml 側は `Js_of_ocaml.Js.export` で次だけを公開する。

```
parse(source)             -> JSON { ok, tokens, ast, lineMap, errors }
astSexp(source, showLine) -> JSON { ok, text }   // parse_viewer.py --format sexp と一致
astDot(source, showLine)  -> JSON { ok, text }   // parse_viewer.py --format dot  と一致
typeInfo(source)          -> JSON                // struct レイアウト・sizeof（B2 着手時に足す）
```

`lineMap` は前処理後の行番号と元ソースの行番号の対応表である。
AST の行番号は前処理後のテキスト基準（`#include` の展開で行がずれる）なので、
エディタの行ハイライトはこの表で写してから行う。

AST JSON の各ノードには Web UI 固有の `sourceRanges: [{from, to}]` を付ける。
`from` / `to` は元ソース上の UTF-16 半開区間で、CodeMirror の位置と直接対応する。
Menhir が保持する前処理後バイト範囲を、前処理器が生成する区間マップで元ソースへ写す。
通常コードは文字単位で対応し、`#define` の展開結果と include 先由来の部分は
誤った箇所を示さないよう範囲を付けない。S 式と DOT にはこのメタデータを出さない。

TypeScript 側にはこの JSON に対応する型定義を手書きで置き、
コアの出力が型どおりであることをテスト1本で検査する。スキーマ定義を二重に持たないためである。

### 3.4 ディレクトリ構成

```
dev/web/
├── core/   # OCaml 言語処理コア（lib = 本体、cli = 黄金テスト用、js = ブラウザ API）
└── app/    # TypeScript + Vite フロントエンド
```

現状の詳しい構成は [`../web/README.md`](../web/README.md) を単一の出典とする。

- `workbook/ocaml/support/` を `web/` 側に**コピーしない**。dune のディレクトリ参照で取り込み、二重管理を避ける
- シミュレータが実装する範囲は、参照コンパイラが実際に出す命令に合わせる。現状は命令25種で足りる。

  ```
  add addi and beqz call div j la lb ld li lw mul neg or rem ret
  sb sd seqz slt snez sub sw xori
  ```

  ディレクティブは8種（`.text` `.globl` `.data` `.bss` `.byte` `.word` `.dword` `.zero`）
- libc シムの範囲は [`workbook/docs/language_spec.md`](../workbook/docs/language_spec.md) の `lib.h` 宣言に合わせる。
  `printf` / `malloc` / `exit` / `strlen` / `strcmp` / `strchr` を実装し、
  `fopen` / `fread` / `fclose` / `fprintf` はセルフホスト専用なので当面対象外とする

## 4. 資料との一致をどう保証するか

OCaml 版と Python 版では AST の内部表現が異なる。

| | Python（`scaffold/ast_def.py`） | OCaml（`ocaml/support/ast_def.ml`） |
|---|---|---|
| ノード | 文字列 `kind` を持つ平坦な `Node` | 代数的データ型（`Binary of { op; lhs; rhs }` など） |
| 型 | 文字列 `ty_str`（`"int*"` など） | 構造化された `ty`（`TyPtr TyInt` など） |

放置すると**ウェブアプリの木と handout の図がずれる**。次を契約として固定する。

- **正は Python 版**（`scaffold/parse_viewer.py`）とする。handout の AST 図19枚はこの出力から生成されており、
  資料側を動かす方がコストが高い。OCaml コアの `astdump` を Python の出力に合わせる
- 黄金テストを CI に置く。全 `workbook/**/tests/*.c` について、
  `parse_viewer.py --format sexp` と コアの `astSexp` がバイト一致すること、
  `--format dot` と `astDot` も同様であることを検査する
- 副次的に、これは OCaml 参考実装のパーサが Python 版と同じ木を作ることの検証になる。
  現状これを確かめる仕組みが無いので、単独でも価値がある
- **シミュレータの正しさは qemu との照合で担保する。**
  参照コンパイラが生成したアセンブリを qemu と node 上のシミュレータの両方で実行し、
  終了コードと標準出力を突き合わせる。これはローカルと CI でのみ走らせる

> **実装時の記録（2026-07）**: `make sim-test`（`web/app/test/qemu-conformance.ts`）が
> workbook の全テスト 104 本中 102 本で qemu と一致している（残る2本は `main` を持たない
> 補助ソースで対象外）。突き合わせ先を `.ans` ではなく **qemu の実測値**にしてあるのは、
> ここで試験したいのがコンパイラではなくシミュレータだからである。

一致が取れる見込みはある。比較演算子の正規化（`a > b` を左右入れ替えで `Lt` にする）は
Python 版と OCaml 版で既に同じ規約になっている。

> **実装時の記録（2026-07）**: 黄金テスト（`web/core/golden_test.py`）は
> 138 ファイル × 4 通り中 528 通りで一致している（残る 6 通りは両実装とも拒否で skip。
> 内訳は L2 の複合代入 3 件 + L3 の可変長引数 3 件）。
> 導入の過程で OCaml 参考実装の実バグを 1 件検出し修正した
> （menhir では働かない `Parsing.symbol_start_pos` による行番号の全損）。
> 「ウェブアプリが参考実装の検証を兼ねる」という本章の狙いが初回から機能した形である。
> typedef 廃止により、typedef 別名の字句フィードバック問題と、それに伴う
> astdump 側の別名逆引き機構は仕組みごと不要になった。

## 5. 論点と割り切り

1. **学習者の成果物は Python である。**
   OCaml + TypeScript の構成だけでは「自分の `mycc.py` をブラウザで動かす」体験は作れない。
   必要になった時点で Pyodide を第2エンジンとしてシミュレータの前段に足す、という二段構えにし、初期スコープからは外す。
   スキャフォールドは標準ライブラリしか使っていないので、Pyodide でそのまま動く見込みである
2. **答えを見せる導線に注意する。**
   A3 は参照実装（`ocaml/komaNN.ml`）の出力を見せることになる。
   これは既に `workbook/ocaml/` として配布済みなので新規の流出ではないが、
   ワンクリックになると「先に答えを見る」導線が強まる。
   既定は AST 表示のみとし、コード生成の表示は明示操作の後ろに置いて、
   `workbook/ocaml/README.md` と同じ注意書きを添える
3. **Private リポジトリ `../c-comp-design/teacher/answers/` は配信物へ入れない。** 4章の検証でのみ使う
4. **Wasm-GC の対応ブラウザ**は Chrome 119 以降 / Firefox 120 以降 / Safari 18.2 以降。
   js_of_ocaml 出力を同梱してフォールバックする
5. **ソース位置の粒度。** AST ノードは元ソース上の文字範囲を持ち、hover で一時表示、
   クリックで固定表示する。通常コードは構文要素全体を正確に示す。
   `#define` 展開結果と include 先には編集画面上の同一範囲がないため、現状はハイライトしない
